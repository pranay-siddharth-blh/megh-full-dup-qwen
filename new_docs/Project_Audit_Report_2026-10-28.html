My honest assessment

The state of the project

The architecture is sound, and the team has been disciplined. Every regex, gate and guard cites the incident it fixes, and 3,910 tests pass. The weakness is underneath that discipline. Most correctness guarantees are string checks layered over a sampling model, and several of those checks match substrings when they should compare exactly:

  • the scope guard accepts SOUTH WEST GARO HILLS for WEST GARO HILLS;
  • the year guard accepts LIMIT 2023 as a year filter;
  • the number check accepts a misquote of 6,563 on 1,494,437.

None of these is a big bug alone. Together they mean a wrong figure can reach an officer with every check passing. Nothing measures this, because there is no automatic accuracy gate.

The second real risk is access control. A district officer can see every other district's figures by asking a normal question, such as "Focus Plus beneficiaries by block". A tenant admin can reset the super_admin's password. For an internal government tool, these matter more than external threats.

The third risk is the process. The docs have grown too big to read: KNOWN_ISSUES is 314 KB and has duplicate ids. Parallel sessions already collide: today I found another session's uncommitted table work that overlaps three of my tasks.

Does the bot use the Qdrant Metadata_* collections?

No. Neither the knowledge path nor the NL→SQL path reads them. No code anywhere in app/ names them; the only mentions are docs saying "not ours, never touch" (CLAUDE.md:246, ARCHITECTURE.md:439, HANDOFF.md:694). The knowledge path reads only megh_scheme_kb_v4, and conversation memory reads only megh_conversation_memory_1024.

Verified on 28 Oct, read-only: there are 7 collections, 4,016 points, 1024-dim, cosine. Each point carries a text field and typed payload: column meanings with synonyms and sample values, entity values with row counts and parent places, formulas with SQL expressions, aggregation and NULL rules, clarification rules, the join graph, and example question→SQL pairs. They were embedded with our own model: re-embedding their text through our gateway's qwen3-embedding gives cosine 0.9999 to 1.0 against the stored vectors. So they are directly searchable with no re-embedding.

The problem

  • A missed capability, not a bug. The bot works without them. But SQL generation gets its schema from the hand-written schema_context.py, a large static block that falls back to all schemes (KI-011) and drifts from the SME YAMLs (KI-010). A question-relevant index of exactly that knowledge already exists and goes unused.
  • Four of the six scheme collections describe a different database layout from the curated views the bot queries. Fed to the SQL model as they are, their column names and example SQL would steer it toward tables that are not in its schema, which means more repairs and more wrong SQL.
  • The bot does not own or control them. Another team owns them, there is no versioning contract, five of the nine source YAMLs are not in our repo, and some entries are flagged needs_sme_confirmation.
  • They are unprotected. Qdrant has no API key (SEC-07), so anyone who can reach it could rewrite them. Putting them into SQL prompts would add a prompt-poisoning path.

The best solution (task RAG-06)

  • Do not connect them to the officer-facing knowledge path. They are schema metadata, not scheme guidance.
  • Use them as an optional, validated schema-retrieval step for SQL generation, starting with the two collections that match (CM Elevate, Focus Plus).
  • Check every retrieved item against the live catalogue (schema_introspect). Drop any item whose table or column is not live. Never insert example SQL unless SQLGlot parses it and it references only live curated objects.
  • Run in shadow mode first (log what would be added), then A/B on the golden set, then switch on per scheme behind a flag. If it is not faster or more accurate, leave it off.
  • For the other four, ask the owner whether that layout is a planned new schema or the raw layer. Agree a version pin (schema_version plus content_hash) and a read-only key for the bot.

    Rules every session follows

    • Branch: name it task/<id>. Cut it from Main only after the tasks listed in its "start after" have merged. Merge through the Bitbucket merge queue, which tests each PR on top of everything already queued.
    • Docs: edit only your task's pre-made stub in CURRENT_STATE and HANDOFF (DOC-02 creates them) and your own KI detail sections. Never edit the KI summary table, the TESTING history table or the "Last updated" lines; the integrator updates those at merge.
    • Ids: new KI ids come only from your track's range (shown on the board). New decisions are written as D-<task id>, and the integrator numbers them from D-074.
    • Pipeline helpers: prefix every new pipeline name with your file and task, for example _c11_sql01_. A duplicate top-level name silently replaces the other one (KI-413). Run tests/test_pipeline_namespace_2026_10_26.py before every PR.
    • config.py and .env.example: add settings next to related ones, in their own commented block. Never add at the end of the class, and never reorder.
    • Frontend: never commit web/app. Before a PR, git diff --name-only origin/Main...HEAD -- web/app must be empty. The integrator builds once after the last frontend merge.
    • Requirements: only QA-02 (wave 0) edits the requirements files.

    Integration checklist after each wave

    1. Run the full pytest command from TESTING.md §2 (baseline 3,910 passed and 3 skipped at HEAD; about 3,932 once P0 is in). After QA-02, pytest tests -q must finish too.
    2. Run all 14 script suites; all must pass.
    3. Run the namespace test and the duplicate KI and D id tests (from QA-02).
    4. Run cd frontend && npm ci && npm run build and commit web/app. The node card and table tests must pass, not skip.
    5. On the VPN: live_context_validation.py with caches on and off, nl2sql_eval --fail-on-regression, rag_eval, and one in-process answer per scheme as a district officer.
    6. Restart on port 8401 and check /health, /megh-chat and /admin-ui.
    7. Integrator only: update the KI table, the TESTING history and the "Last updated" lines.

Context memory audit

How well the chatbot remembers a conversation today, what it would take to run it in production for district and state officers, and the order in which to do that work.

Where we stand

The memory now behaves the way the user rules ask for in almost every scripted conversation. It is not production-ready yet. The gaps are mostly not in the answers. They are in who can reach a conversation, how long it is kept, how failures are seen, and how often the rules themselves change.

Verdict: pilot-ready inside the office network, not production-ready. Conversation behaviour is close to target (99.2% of live turns today; target 99% on a signed rule set). Five things block a government production launch:

  • Any signed-in user who has another user's conversation id can continue that conversation and see its history (F1).
  • One answer served from the shared cache makes the chat forget its other topics, so "go back to MGNREGA" stops working (F2).
  • Conversations are kept forever, and deleting one leaves copies in two other stores (F3).
  • The rules for carrying the year and the idle window have changed several times in a week and are not signed off (F5).
  • There are no numbers in production that would show a memory failure before an officer reports it (F8).

What context memory is

An officer rarely asks one complete question. They ask "MGNREGA person-days in East Garo Hills in 2024-25", then "and West Garo Hills?", then "what about PMAY-G?". Context memory is what lets the second and third messages be answered correctly without repeating everything. These are the rules it follows today (D-056, D-061, D-065).

Rule 1 · New chat

Ask, one thing at a time

Nothing is assumed. If the question does not name them, the bot asks for the scheme, then the district, then the year, one pause each, with chips to tap.

"How many job cards?" → Which scheme? → Which district? → Which year?
Rule 2 · Complete question inside a chat

The question wins

A question with its own scheme and measure inherits nothing. If it has no year, the bot asks for the year rather than picking the latest one. The answer is marked "(new question)".

"PMAY-G houses completed in East Garo Hills in FY 2023-24" → banner: PMAY-G · East Garo Hills · FY 2023-24 (new question)
Rule 3 · Follow-up

Fill only the gaps

A fragment or a reference ("and", "what about", "same for", "that") keeps everything it does not change. A vague one uses the only open topic, or asks which one when two are open.

"and in West Garo Hills?" → MGNREGA · West Garo Hills · FY 2024-25

Around these rules sit: a 50-turn window, up to 8 topics that can be returned to ("go back to MGNREGA"), an 8-hour idle window followed by a "Continue with …" chip, clarification pauses that survive a worker change, and a scope banner on every answer.

Findings

Ranked by what they would cost in production. F1 and F2 are new and were confirmed today; the rest were read in the code or the project records.

HighF1 · A conversation is not tied to the user who owns itsecurity
What
The browser sends the conversation id. The server accepts it as is (routers/query.py:144-155). It never checks that the stored conversation belongs to the caller: session_store.ensure (session_store.py:306-324) does not compare user ids, the snapshot is loaded by id alone (conversation_store.py:377-399), the save upserts on id alone (:348-374), and the paused graph run uses the same id. The conversation history pages do filter by user; the question path does not.
Live
Checked with the real SessionStore.ensure: officer B asking with officer A's conversation id gets the same session object, owner still A, and sees A's scheme, district and last question. The live two-account probe is written and waits for the VPN.
Limits
Ids from the web UI are random, so guessing one is hard. Data access is still re-checked against the caller's own scope, so no restricted figures leak. Earlier questions, answers and places do.
Fix
Store the owner on first use; on a mismatch refuse (403) or start a fresh conversation. Add AND user_id = $n to the load and save SQL. Add a two-account test to the harness.
HighF2 · One cached answer wipes the chat's topicscorrectness · new
What
Every saved turn raises the conversation's revision by one. topic_memory.checkpoint (topic_memory.py:401-404) treats a jump of more than one since it last ran as "another worker served turns I never saw" and drops every topic. It only runs when a turn goes through the graph. A cache hit, a greeting, a reset or a Stop still saves a revision, so the next real turn sees a jump of two and resets.
Evidence
Direct check with the real functions: 1 topic before, 0 after. The live probe (two topics, one cached answer, then “go back to MGNREGA”, with a no-cache control chat) is written and waits for the VPN.
Effect
"Go back to MGNREGA", "repeat my first question" and the "which topic?" chips silently stop working after the first cached answer. Caches are on in production and the harness runs with them off, which is why the harness has not caught this.
Fix
Record the revision a worker itself writes (in sync_out) as seen, or run the checkpoint on every saved turn. Add a regression test and run the harness once with caches on.
MediumF3 · Conversations are kept forever, and deletion is partialprivacy · retention
What
app.conversations.context_state and the turn rows have no expiry. Deleting a conversation (conversation_store.py:262-276) leaves its Qdrant memory points and any checkpoint rows. Purging a user keeps their conversations (appdb.py:348-353). A snapshot has no size cap: up to 8 topic answers of 2,000 characters plus 160 ledger answers of 300 characters each. The worker copy keeps full answers.
Why it matters
Questions name villages, groups and people's schemes. A government deployment needs a written retention period and a deletion that actually deletes; check it against the Digital Personal Data Protection Act, 2023 and the department's records policy.
Fix
One retention setting (for example 180 days) with a daily purge across all four stores; cascade deletes; a snapshot size cap; trim answers in the worker copy.
MediumF4 · Five separate checks decide "is this a follow-up?"consistency
What
context_policy.turn_kind, the follow-up gate in c14_turn_stages.py:1293-1300, the cache gate is_cacheable (routers/query.py:416-462), continuation_signals and the conversation layer each read the sentence with their own word lists. When they disagree, the result is a wrong inheritance or, worse, a shared cached answer for a follow-up. KI-337 ("show me for X" served from cache as a knowledge answer) was exactly this.
Fix
Decide the turn kind once per turn, store it on the turn, and have the cache gate, the rewrite and the banner read that one value. Longer term, the typed query-plan step from the NL→SQL benchmark report replaces most of these word lists.
MediumF5 · The rules keep changing and are not signed offgovernance
What
The year rule for a new question in a running chat changed four times in four days: keep the chat's year (KI-331, 19 Oct), carry place and year (D-056, 21 Oct), latest year (D-061, 22 Oct), ask the year (D-065, 22 Oct night). The idle window moved 30 min → 4 h → 8 h; the 22 Oct addendum asked for 30 min and is still open. Harness scenario U5 still encodes the KI-331 behaviour (marked DOCUMENTATION CONFLICT).
Why it matters
Each change rewrites code, tests and scenarios, and earlier fixes are re-broken. Officers will be trained on one behaviour.
Fix
A one-page "conversation rulebook v1" signed by the department, with the 139 scenarios as its acceptance test. Changes after that go through a short change request.
MediumF6 · Time limits disagree with each otherreliability
What
Idle window 8 h (config.py:369,382); a paused graph run is swept after 30 min (config.py:605); stop → continue is capped at 30 min (D-050); the pause itself lives on in the session for 8 h, so a reply after 30 min resumes from the fallback copy. CURRENT_STATE records that the deploy .env files on the VMs still hold 30 min and 8 turns (they are not in the repository, so this could not be checked). Comments in tests/test_stop_continue.py still say 4 h.
Fix
One idle setting that drives all four, a check at startup that logs the values in force, and the deploy files updated to match.
MediumF7 · Two turns at once: one is silently lostreliability
What
The save is versioned, and the first writer wins (session_sync.py:115-119). The losing request has already answered the officer, but its memory update is dropped with only a log line. The lock that serialises turns works within one worker only (pipeline_graph.py:640-648); production runs 2 workers on each of 2 VMs without stickiness.
Fix
Refuse a second turn on a busy conversation (409, the UI waits), or reload and re-apply. Count stale writes as a metric.
MediumF8 · Memory failures are invisible until an officer reports oneobservability
What
There is a JSON decision log per turn (pipeline_decision, 95 call sites), but /metrics counts only requests, routes, errors and latency. Nothing counts follow-ups vs new questions, rejected rewrites, topic resets, sync failures, stale writes or expired pauses. The decision log also writes question text, although its own docstring says it never does (context_budget.py:111-112).
Fix
Eight counters (listed under Production target), an admin panel tile, and alerts on sudden changes. Strip question text from the decision log or mark it as personal data.

How we get there

Three steps. Each ends with a check that has to pass before the next starts.

Step 1 · Close the gaps

About one week
  1. F1: bind each conversation to its owner; two-account harness scenario.
  2. F2: fix the topic reset; regression test; one harness run with caches on.
  3. Decide the idle window and U5 (see below); one setting for all time limits (F6); update the deploy .env.
  4. Fix or re-scope the failing harness chats and KI-363, KI-364, KI-396.
  5. Make the live suites save dated results; refresh CONTEXT_AND_LANGGRAPH.md (F10).

Exit: harness ≥ 99% with caches off and on; P1 refused; 0 High issues.

Step 2 · Make it safe to run

Two to three weeks
  1. Retention period, daily purge across all stores, cascade delete, snapshot cap (F3).
  2. The eight memory counters, an admin tile and alerts (F8).
  3. Busy-conversation handling and a stale-write counter (F7).
  4. One turn-kind decision per turn, read by the cache gate and rewrite (F4).
  5. Offline suite on every merge; live harness nightly from a machine on the VPN.
  6. Sign the conversation rulebook v1 (F5).

Exit: three nightly runs in a row ≥ 99%; rulebook signed; retention live.

Step 3 · Prove it with officers

Three to six weeks
  1. Load test at the agreed number of concurrent officers on the production layout.
  2. External security audit of the chat API.
  3. UAT with officers from two districts; their real chats become new harness scenarios.
  4. Pilot the typed query-plan step in shadow mode (logs only), compared against today's word rules, before any switch.

Exit: signed UAT, closed audit findings, load target met: production launch.

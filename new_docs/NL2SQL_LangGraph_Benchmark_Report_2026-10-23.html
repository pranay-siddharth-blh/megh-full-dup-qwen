Megh One AI's LangGraph NL→SQL chatbot: required features, benchmarks and gaps

Date: 23 Oct 2026 Branch: update/2026-10-22 @ 6c95632 + uncommitted work Scope: 6 scheme datasets, megh_db.curated, LangGraph orchestrator

Short answer: we have built most of what a production NL→SQL chatbot needs. When the bot gives a figure, it is almost always correct. In the 23 Oct audit, every figure in about 110 live answers matched the database. On the 74-question held-out set, accuracy was 97.3%.

We fall short in four places:

  • Understanding real officers' wording. Testers' own phrasing scores 79–93% on the weakest sheets.
  • Speed under load. Answers take 10–24 s with only 4 users at once.
  • Measuring accuracy on every change. Two large accuracy drops reached the code while every unit test stayed green.
  • Least-privilege data access. Model-written SQL runs as the main database login.

The common cause is that question understanding is ~3,500 hand-written phrase rules instead of one structured query-analysis step.

2. What a LangGraph NL→SQL pipeline specifically should have

LangGraph adds explicit state, branching, pausing and checkpointing to a pipeline. A mature NL→SQL graph uses all of them, and keeps business logic out of the graph wiring.

START → context → edge → followup → route ─KNOWLEDGE→ knowledge ──────────────────────┐ └─DATA→ data_context → scope_scheme → entities │ → clarification_gate → deterministic → sql_generate → authorize │ → execute_attempt ─error→ repair ─→ execute_attempt (≤ 3 repairs, re-authorised) │ └─rows→ post_rows → compose → guarantees → assemble ────────────────────────────┤ any node: ClarificationNeeded → pause_gate [interrupt()] ─resume→ context │ finalize → context_update → END
LangGraph capabilityStatusHow we use it / what is missing
Typed graph state, plain-data, serialisableHaveMeghalayaGraphState; Decimal and dates round-trip exactly; fresh state every turn
Thin nodes, logic in stagesHave21 nodes wrap stage functions; LangGraph is the only orchestrator (D-032, D-036)
Conditional edges + bounded repair loopHaveexecute_attempt ⇄ repair, capped by MAX_SQL_REPAIRS
Human-in-the-loop with interrupt() / resumeHaveClarification chips pause the graph. A resume authorises with the resuming request's scope
Durable checkpointer shared across workersHavePostgres checkpointer in app.*; only paused threads are kept, swept after a TTL
StreamingPartialSSE draft text with checks on the full answer (D-039). There are no per-node progress events, such as "understanding… writing SQL… checking…"
Parallel fan-out (Send / map-reduce) for multi-scheme workPartialCross-scheme sub-questions run in parallel with asyncio.gather inside one stage. That fan-out is invisible to graph tracing and checkpointing
Query-analysis node producing a validated planMissingNo query_analyzer node; understanding is scattered across rule files

3. Which benchmarks matter, and what "good" looks like

Public NL→SQL benchmarks measure execution accuracy (EX): does the generated SQL return the same result as the gold SQL? They are useful reference points. They are not directly comparable with us, because our database, domain and question style are our own.

Public benchmarkWhat it testsReference level (approximate)Relevance to us
Spider 1.0Cross-domain SQL over ~200 small databasesTop systems ≈ high-80s to ~90% EXLow. Clean schemas, single-turn
BIRDLarge, dirty, real-world databases; external knowledge; efficiencyHuman ≈ 93% EX; leading systems roughly mid-70s to ~80%High. Dirty data and domain knowledge, like ours
Spider 2.0Enterprise warehouses and multi-step agentic workflowsMuch harder; the best agents score well below Spider 1.0 levelsMedium. Shows how hard enterprise NL→SQL is
SParC / CoSQLMulti-turn, context-dependent SQL; clarificationQuestion-level EX well below single-turn scoresHigh. Follow-ups are our main use pattern
Dr.Spider and similar robustness setsParaphrase, typo and synonym perturbationsAccuracy typically drops noticeably under perturbationVery high. This is our main weakness

The figures above are approximate and come from public leaderboards up to mid-2026. Check the current leaderboard before you quote them.

Benchmarks a production chatbot should track (our proposed targets)

A government analytics bot is judged less on leaderboard EX and more on these questions: Is any number it shows ever wrong? Does a different wording give the same answer? Is it fast enough? Is it safe? The targets below come from those questions and from the project's design load of 20–40 concurrent users.

6. Where we are lacking, and why

Ordered by impact on an officer. Each gap names its root cause and a concrete fix.

1Question understanding is rule-based, so new wordings fall through
Evidence
About 3,500 phrase rules (551 Matcher, 1,555 W(…), 948 Seq, 519 Alt) in 36 files. The same concept is listed in 3 places that disagree. Testers' wording scores 79–93% where canonical wording scores 98–100%. Open examples: "FY24" read as 2024-25, "five highest" not read as top 5, "Demdema block" resolved to the village.
Why it matters
Each fix covers one sentence. The next unseen wording takes a different path, and the result is a needless question, a refusal or a wrong year.
Fix
Add one query_analyzer node. It turns every question into a typed plan {scheme, metric, level, place, period, top_n, shape, compare}, validates the plan in code against the registries, and normalises "FY24" and "five" once. Every later stage reads the plan, and the rules shrink to validators. This change needs a DECISIONS entry.
2No accuracy benchmark gates changes
Evidence
The 74-item held-out eval is run by hand; last full run 18 Oct. Unit tests lock in old fixes but do not measure accuracy (KI-017). Two silent regressions in October: Focus Legacy constituencies 55 → 11, CM Elevate Legacy 300 → 179.
Fix
Grow the gold set to ≥ 300 items: ~50 per scheme, plus paraphrase variants (typos, Hinglish, number words, FY formats), multi-turn chains and cross-scheme items. Run it nightly and before every merge with --fail-on-regression. Track the clarification rate and the wrong-number rate as separate metrics.
3Latency under load
Evidence
3.3–5.8 s for one user, 10–24 s at 4 users, 10–40 s for cross-scheme questions. A data answer makes 4–6 model calls in a row (up to ~13 in the worst case), all queuing at one vLLM gateway. The design target is 20–40 concurrent users.
Fix
Run a load test at 20/40 users and set a p95 budget per node. Skip the verifier for deterministic or cached SQL. Merge classify and rewrite into the analyzer call. Add a shared cache (Redis) so a hit on one worker is a hit on every worker. Stream per-node progress events so waiting feels shorter.
4Defence in depth on the database
Evidence
Model SQL runs as the main login with superuser allowed (KI-004 / KI-304). Certificate checks to the gateway are off because the CA file is missing (KI-015). Qdrant is on a public IP with no API key (KI-200).
Fix
Set READONLY_DATABASE_URL to megh_readonly and remove the superuser allowance. Install the CA file and refuse to start without it. Put Qdrant behind an API key and a firewall.
5Occasional wrong aggregates from sampling
Evidence
KI-354 (1 in 7), KI-362 (1 in 20), KI-313 (year range narrowed). vLLM batching is not bit-exact at temperature 0, and no seed is sent. The verifier sometimes rejects correct SQL (KI-002), which starts repairs that drift.
Fix
Send a fixed seed. Add the project's usual 3-layer guard (prompt rule + few-shot + deterministic check of the plan against the SQL tree), so the SQL must filter exactly what the plan says. Add self-consistency on hard questions: generate 2 SQLs and compare their results.
6Inconsistent presentation of the same number
Evidence
₹5,237,500.00 in one answer and ₹0.52 crore in another; Western and Indian grouping mixed; NULL drawn as 0; the compare card puts "spent" against "released"; phone cards cut figures off.
Fix
Format money and counts in code after the composer (crore / lakh, en-IN grouping). Show no verdict when the two measures differ in kind. Wrap the welcome cards below 480 px.
7Observability and the feedback loop are not connected
Evidence
Node logs carry no question text. A failed attempt's SQL is not logged (KI-003). The audit table does not hold the SQL. 👍/👎 votes are stored but never reviewed into eval items.
Fix
Store one trace per turn (plan, node path, every SQL attempt, verifier verdicts, timings) in app.* with role-based access. Add an admin triage view where a 👎 becomes a gold-set candidate in one click.
8Policy churn and stale docs
Evidence
Seven behaviour decisions in one day (D-060..066). The CM Elevate rule changed on 12, 19 and 22 Oct. U5 / KI-331 vs D-065 is still open. CLAUDE.md is stale on the verifier model, the reranker and test counts.
Fix
Write each product rule as gold-set items before changing code, so every reversal shows up as a measured change. Get decisions on U5, KI-352, KI-353 and KI-359.

7. Suggested roadmap

Week 1: measure and protect

  1. Read-only DB role; remove superuser; install the CA file; Qdrant API key.
  2. Re-run the 74-item eval on today's code; add it to CI with --fail-on-regression.
  3. Load test at 20 and 40 users; record p50/p95 per node.
  4. Shared number formatter (crore / lakh, en-IN).

Weeks 2–4: robustness

  1. Grow the gold set to ≥ 300 items with paraphrase, multi-turn and cross-scheme cases.
  2. Normalise number words and FY formats once, used by every stage.
  3. Fixed seed; plan-vs-SQL deterministic guard.
  4. Per-turn trace store and a 👎 triage view.

Month 2: architecture

  1. query_analyzer node with a validated typed plan (DECISIONS entry first).
  2. Schema-retrieval node; cross-scheme fan-out moved to LangGraph Send.
  3. Node RetryPolicy and time budgets; per-node progress streaming.
  4. Retire phrase rules that the plan makes redundant, measured on the gold set.

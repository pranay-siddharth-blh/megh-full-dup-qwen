The issuetopic_memory.checkpoint wipes every topic when the revision jumps by more than one. Every saved turn bumps the revision, but only graph turns run checkpoint. So these all wipe the topics:
  • a cache hit;
  • small talk handled by the conversation layer ("how are you?");
  • a typed "stop" with nothing running;
  • an early Stop;
  • every "Continue with …" tap after idle expiry, which restores a stale copy and keeps only one topic.
After a wipe, "go back to MGNREGA", the topic chips and digression recovery stop working. Separately, "go back to Mawphlang" never reaches the ledger, because parse_backward rejects a bare place name.
The solution
  • Delete the stale-jump block (401-404) and the matching docstring lines 33-36.
  • In parse_backward's "go back to" branch, accept a place-only target (entity_resolver.place_only) as BackRef(None, …). In resolve_reference, skip the model call for a bare-place ref with no ledger match.
Don't do this
  • Recording mem['rev'] inside sync_out. That couples session_sync to topic_memory internals in order to keep a guard that protects nothing.
Evidence
  • topic_memory.py:401-404 does the reset. Its reason ("another worker served turns") is obsolete: topics travel in the same durable snapshot.
  • test_cache_hit_context.py:59 replaces sync_out with a no-op, and the in-process harness never calls it. That is why no test caught this.
  • parse_backward("go back to Mawphlang") returns None, while "go back to the Mawphlang one" works. _score already matches places correctly.

CTX-01Mediumwave 1bKI-399KI-028

Conversation ownership and turn integrity

AreaContext memory
WaveWave 1b: parallel
Start afterREL-02
UnblocksCTX-04, CTX-06, RAG-05, UI-02, QA-03
New KI idsKI-470–499
REPRODUCED: ensure('sid','alice') then ensure('sid','bob') returns alice's session. Severity lowered: the attacker must be logged in and hold another user's id (about 46 random bits), and figures are still re-authorised. This card merges v1 CTX-01 and CTX-03.
The issueNothing checks that a session id belongs to the caller. A user holding another's id inherits that chat's context, can ask "what did we discuss?" and receive the other user's questions, and overwrites the other user's state. Within one worker, two concurrent requests on one id interleave state, because only the graph run is locked. A Stop can save half-applied state. The client's 75 s limit applies to the whole stream, even while pings keep it alive.
The solution
  • Ownership: load_context_state also returns user_id. sync_in returns "foreign" without applying the snapshot. _answer returns 403 (and logs it) when the in-memory or durable owner differs from scope.user_id, and sets a flag so _remember_stopped skips. Add a SQL backstop: AND user_id IS NOT DISTINCT FROM $n in the upsert's ON CONFLICT … WHERE.
  • Concurrency: add a router-level per-session asyncio.Lock dict, as a wrapper. Keep the name _answer and rename the inner function. Do not reuse the graph's lock: it is not re-entrant and would deadlock.
  • Cancel: snapshot the Session when the turn starts, and restore it in _remember_stopped before recording stopped_ctx.
  • Client: make the stream timeout an inactivity timer that resets on any chunk, pings included.
Don't do this
  • Namespacing the graph thread_id by user. It orphans live paused threads at deploy.
  • 409 plus UI retry, or a server-side request_id dedup table. These are over-built; count stale writes instead.
Evidence
  • query.py:143-170 _session_id; session_store.py:306-324 ensure; conversation_store load_context_state (~379, session_id only), save_session_state (350) and _persist_turn (40-124).
  • pipeline_graph.py:789 locks only the graph. _remember_stopped (query.py:176-198) saves unconditionally.
  • api.js:96 and :134 apply the 75 s limit. : ping frames are skipped before gotEvent.
  • The history routes are already owner-scoped.

REPRODUCED: ensure('sid','alice') then ensure('sid','bob') returns alice's session. Severity lowered: the attacker must be logged in and hold another user's id (about 46 random bits), and figures are still re-authorised. This card merges v1 CTX-01 and CTX-03.

THE ISSUE
Nothing checks that a session id belongs to the caller. A user holding another's id inherits that chat's context, can ask "what did we discuss?" and receive the other user's questions, and overwrites the other user's state. Within one worker, two concurrent requests on one id interleave state, because only the graph run is locked. A Stop can save half-applied state. The client's 75 s limit applies to the whole stream, even while pings keep it alive.

EVIDENCE
- query.py:143-170 _session_id; session_store.py:306-324 ensure; conversation_store load_context_state (~379, session_id only), save_session_state (350) and _persist_turn (40-124).
- pipeline_graph.py:789 locks only the graph. _remember_stopped (query.py:176-198) saves unconditionally.
- api.js:96 and :134 apply the 75 s limit. : ping frames are skipped before gotEvent.
- The history routes are already owner-scoped.

THE SOLUTION
- Ownership: load_context_state also returns user_id. sync_in returns "foreign" without applying the snapshot. _answer returns 403 (and logs it) when the in-memory or durable owner differs from scope.user_id, and sets a flag so _remember_stopped skips. Add a SQL backstop: AND user_id IS NOT DISTINCT FROM $n in the upsert's ON CONFLICT … WHERE.
- Concurrency: add a router-level per-session asyncio.Lock dict, as a wrapper. Keep the name _answer and rename the inner function. Do not reuse the graph's lock: it is not re-entrant and would deadlock.
- Cancel: snapshot the Session when the turn starts, and restore it in _remember_stopped before recording stopped_ctx.
- Client: make the stream timeout an inactivity timer that resets on any chunk, pings included.

DO NOT
- Namespacing the graph thread_id by user. It orphans live paused threads at deploy.
- 409 plus UI retry, or a server-side request_id dedup table. These are over-built; count stale writes instead.

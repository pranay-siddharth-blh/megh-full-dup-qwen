Close the geography leaks in authorize()

AreaSecurity & access
WaveWave 1a: parallel
Start afternothing (wave start)
UnblocksSEC-03
New KI idsKI-450–469
REPRODUCED with real auth.authorize calls for a district officer pinned to EAST KHASI HILLS.
The issueauthorize only checks that the district or block values named in the SQL are allowed. So <>, NOT IN, OR 1=1, an unfiltered UNION branch, a CTE with OR … IS NOT NULL, and a block from another district are all allowed. Worse, no trick is needed: GROUP BY block_name_raw, district_name_raw or ac_name is treated as statewide, so an ordinary "Focus Plus beneficiaries by block" shows a district officer every block in the state. There are three fail-open scope bugs as well:
  • a scheme-name typo grants all six schemes;
  • an unknown role falls back to the analyst role (all geography);
  • a bogus granularity_cap crashes every question with ValueError.
The solution
  • Add a new sql_ast function. For every SELECT that reads a base view directly, it returns the EQ and IN geo predicates found among the top-level AND conjuncts of its WHERE. NOT, NEQ, LIKE and OR never count.
  • For a geo-restricted user at finer-than-state grain, require every such SELECT to carry one, with all values allowed. A block counts only if entity_resolver.block_parent_district is an allowed district.
  • Add one geo-column registry in auth.py and use it in infer_granularity, _districts_in_sql and _blocks_in_sql: district = lgd_district, district_name_raw; block = lgd_block, block_name_raw; AC = ac_name, assembly_constituency_name, counted at block level.
  • In scope_from_user: an empty scheme intersection gives []; the cap is the coarser of the role cap and the user cap; an unknown cap is ignored; an unknown role gets public.
Don't do this
  • Changing filter_values. It has 13 other callers.
  • Injecting the scope predicate with transform. The views use different geo column names, and the result rows would change.
Evidence
  • sql_ast.filter_values (:325) walks every comparison, including NEQ and Not(In), without regard to AND or OR.
  • auth.py:172 (role fallback), :177 (or schemes), :191 (the user cap can widen the role cap).
  • An unfiltered GROUP BY lgd_district and LIKE '%' are already denied correctly.

The issueA tenant admin can do three things to a super_admin:
  • PATCH any user, the super_admin included, to the super_admin role;
  • deactivate the super_admin;
  • worst, reset the super_admin's password through UpdateUser.password.
All seeded users share one tenant, so the tenant check does not protect anyone. Combined with the rd-admin seed password in git history, this is a full takeover path. Separately, the stats cards ignore the user's scheme list.
The solution
  • In update_user and deactivate_user, return 403 when the target is a super_admin, or the body sets role=super_admin, and the caller is not cross-tenant. Forbid changing your own role.
  • Add Pydantic validators to NewUser and UpdateUser: role in ROLE_PERMISSIONS; schemes a subset of the six; cap in GRANULARITY_ORDER. Import those constants from auth; do not edit auth.py.
  • Stats: filter the cards by scope.schemes when responding. The shared cache stays.
Don't do this
  • Per-district stats cards. Statewide totals are allowed for every role, so they add no protection.
Evidence
  • routers/admin.py:115-126 update_user checks only that the role exists and the tenant matches. The super_admin check exists only in create_user (:101).
  • appdb.update_user:333-335 applies the password.
  • stats.py:161-178 serves the cards. They are statewide aggregates, which every role may see, so only the scheme filter is missing.

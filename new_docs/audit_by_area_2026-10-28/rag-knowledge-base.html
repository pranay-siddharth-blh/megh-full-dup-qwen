RAG-04Mediumwave 2KI-402D-067

KB ingestion that is idempotent and notices edits

AreaKnowledge base (RAG)
WaveWave 2
Start afterRAG-02, CTX-04
UnblocksRAG-05, REL-03
New KI idsKI-500–519
CONFIRMED. The size-mismatch delete is the deliberate KI-402 fix and is pinned by a test, so changing it needs a DECISIONS entry. The duplicate-point race is more likely than v1 said.
The issueFour ingestion problems:
  • Every worker on both VMs ingests at startup with random point ids and no lock. On a deploy that needs a rebuild, they race, and duplicate chunks persist: a count of 2N passes the skip check. With multi-query off, duplicates take top-8 slots.
  • Editing a document does not trigger a rebuild on restart.
  • The per-worker KB text cache is never cleared, and can cache an empty KB.
  • Reingest runs inside the HTTP request.
The solution
  • Deterministic uuid5(doc|heading|sha1(text)) ids.
  • Store corpus_hash (source digests plus chunker version) in the payload; rebuild when the first point's hash differs.
  • Rebuild by upserting all ids and then deleting the ones no longer present, instead of recreate-then-fill. That is idempotent under concurrency and leaves no empty window.
  • On a vector-size mismatch, refuse with a CRITICAL log and a degraded /health, as conversation_memory does. Record the reversal of KI-402 in DECISIONS and rewrite the pinned test.
  • Key the text cache on (collection, hash), never cache an empty result, and run reingest in the background with its status in /api/rag/status.
Don't do this
  • Alias swap plus an advisory lock. Not needed once the ids are deterministic.
Evidence
  • main.py:83; kb_ingest.py:749 (skip check), :797 (recreate), :800 (uuid4).
  • rag.py:313 and :368-382 (cache).
  • test_embedding_size_guard_2026_10_24.py::test_a_kb_of_another_vector_size_is_rebuilt pins the delete.

Does the bot use the Qdrant Metadata_* collections?

No. Neither the knowledge path nor the NL→SQL path reads them. No code anywhere in app/ names them; the only mentions are docs saying "not ours, never touch" (CLAUDE.md:246, ARCHITECTURE.md:439, HANDOFF.md:694). Verified on 28 Oct, read-only: there are 7 collections, 4,016 points, 1024-dim, cosine. The problem

  • A missed capability, not a bug. The bot works without them. But SQL generation gets its schema from the hand-written schema_context.py, a large static block that falls back to all schemes (KI-011) and drifts from the SME YAMLs (KI-010). A question-relevant index of exactly that knowledge already exists and goes unused.
  • Four of the six scheme collections describe a different database layout from the curated views the bot queries. Fed to the SQL model as they are, their column names and example SQL would steer it toward tables that are not in its schema, which means more repairs and more wrong SQL.
  • The bot does not own or control them. Another team owns them, there is no versioning contract, five of the nine source YAMLs are not in our repo, and some entries are flagged needs_sme_confirmation.
  • They are unprotected. Qdrant has no API key (SEC-07), so anyone who can reach it could rewrite them. Putting them into SQL prompts would add a prompt-poisoning path.

The best solution (task RAG-06)

  • Do not connect them to the officer-facing knowledge path. They are schema metadata, not scheme guidance.
  • Use them as an optional, validated schema-retrieval step for SQL generation, starting with the two collections that match (CM Elevate, Focus Plus).

  • Run in shadow mode first (log what would be added), then A/B on the golden set, then switch on per scheme behind a flag. If it is not faster or more accurate, leave it off.
  • For the other four, ask the owner whether that layout is a planned new schema or the raw layer. Agree a version pin (schema_version plus content_hash) and a read-only key for the bot.

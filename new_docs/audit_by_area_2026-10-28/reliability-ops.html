Config hygiene, a non-stream deadline, safe retries

AreaReliability & ops

New KI idsKI-590–609
CONFIRMED. Two parts of the v1 fix would have caused harm: deleting settings would break boot, and a global 110 s cap would break streamed answers.
The issueFour settings are never read: SQL_GENERATION_MAX_RETRIES, SQL_GUIDED_DECODING_ENABLED, MULTITENANCY_ENABLED and PORT. But Settings rejects unknown keys, so deleting them breaks boot for any .env that still sets one. The non-stream /api/query can run 60 s × 6 parts while nginx cuts it at 120 s; the streamed route is safe because of its pings. Model calls never retry on a connection error. wait_for(_gate.acquire()) can leak a semaphore slot on Python 3.11 when it is cancelled.
The solution
  • In one commit: switch to model_config = SettingsConfigDict(env_file=".env", extra="ignore"), then delete the four fields. This also clears the Pydantic warning.
  • Cap the deadline on the non-stream route only, at 110 s.
  • Retry once, with jitter, on httpx.ConnectError and ConnectTimeout only.
  • Wrap async with asyncio.timeout(...) around _gate.acquire().
  • Add a test that every Settings field is referenced outside config.py, with an allowlist.
Don't do this
  • Deleting the settings before switching to extra="ignore". Boot fails.
  • A global 110 s cap. It would cut streamed multi-scheme answers that work today.
  • Retrying on 502/503. That adds load to a gateway that is already saturated.
Evidence

Redis failure backoff and a build stamp on cache keys

AreaReliability & ops
WaveWave 1a: parallel
Start afternothing (wave start)
Unblocksno task waits on this
New KI idsKI-590–609
CONFIRMED. Impact lowered: Redis is not set up on dev, and a deploy clears the per-worker cache anyway.
The issueWhen Redis is down, every request retries the connection under one lock, at 1.5 s per try, so the requests queue behind each other. The docstring of _redis() claims the failure is cached; it is not. A shared Redis would also serve answers from an older build.
The solution
  • Remember the failure time and skip reconnects for 30 s.
  • Add APP_BUILD (the git sha) to REDIS_CACHE_PREFIX.
Don't do this
  • An admin flush endpoint. It would clear only the one worker it lands on (2 workers × 2 VMs). If flushing is needed, keep a generation number in Redis.
Evidence
  • cache.py:37-68, keys at :93-96.

Request ids in logs, a cheap /health, bounded rate-limit memory

AreaReliability & ops
WaveWave 3: last
Start afterCTX-04, RAG-04, SEC-05
Unblocksno task waits on this
New KI idsKI-590–609
CONFIRMED. Corrections: the files live in app/middleware/, and X-Request-ID is already trimmed to 64 characters.
The issueThree operability gaps:
  • Log lines carry no request id.
  • An anonymous /health runs DB, Qdrant and Redis probes and can block for 30 s.
  • Rate-limit keys are never deleted, which SEC-05's spoofable IPs made a memory risk.
The solution
  • Add a logging.Filter that injects the request id and user.
  • Cache /health component results for 5 s, with a 2 s timeout per probe.
  • Drop empty rate-limit deques. Validate X-Request-ID to letters, digits and hyphens.
Don't do this
  • Moving to pure ASGI middleware in this task; that is a larger change.

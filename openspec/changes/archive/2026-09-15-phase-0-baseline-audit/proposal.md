# Phase 0 — Baseline Audit & Requirement Mapping

## Status
Complete — no code changes shipped in this phase. Output is a written audit
(`docs/baseline-audit.md`) plus the six scoped follow-on change proposal stubs
in this `openspec/changes/` directory.

## Why

We have a Grant Thornton solution proposal describing a 15-node LangGraph
pipeline with strict security, durability, and observability guarantees
(`GrantThornton_Solution_Proposal_1 (1).pdf`, Sections 3–12), and an existing
production Meghalaya conversational analytics app that already implements
significant pieces of this under different names and structures:

- `app/pipeline.py` — monolithic orchestration (scope detection, followup
  rewriting, scheme clarification, SQL extraction) with no LangGraph, no
  typed node boundaries, no durable checkpointing.
- `app/db.py` — single pool, `_assert_safe()` guarding raw SQL text before
  execution (regex/string-based, not an AST validator).
- `app/auth.py` — `UserScope`, `authorize()`, `infer_granularity()`,
  file-based `audit()` — role/geography/scheme scoping already exists but
  its relationship to `db.py`'s connection pool and to SQL repair was
  unverified going into this phase (now verified — see below).
- `app/session_store.py` — `SessionStore`, `ConversationState`, `Turn` —
  in-memory or partially-persisted session state; ownership enforcement
  and cross-tenant isolation was unverified going into this phase (now
  verified — see below).
- `app/entity_resolver.py`, `app/schema_introspect.py`,
  `app/context_manager.py`, `app/semantic_cache.py`, `app/followups.py`,
  `app/premise_check.py` — partial equivalents of proposal nodes 5.2, 5.6,
  5.8, and the clarification/default rule nodes (5.3/5.5).

Jumping straight to implementation against the Grant Thornton document
(as a single large instruction set) risks two failure modes: (1) treating
proposal-section documentation as if it already describes shipped code,
and (2) silently dropping requirements when the working set is too large
for one reviewable change. Phase 0 exists to produce an evidence-based,
file-and-function-level map of current state before any Phase 1+ change
is scoped or approved.

## What Changed

- Produced a node-by-node classification (Implemented and verified /
  Partially implemented / Missing / Present but unsafe / Requires live
  deployment verification) of proposal Sections 5.1–5.15 against the
  actual files in this repo, citing exact function names and line-level
  evidence — not docstrings or comments taken at face value.
- Produced an equivalent classification of the **Section 11** security
  requirements (session ownership, DB privilege separation, SQL AST
  validation, execution controls, repair re-authorization, production
  config hardening) against `app/db.py`, `app/auth.py`, `app/security.py`,
  `app/session_store.py`. Note: the original brief for this phase cited
  "Section 3" for security — the actual PDF's security section is
  **Section 11** ("Solution Overview" is Section 3). Audited against the
  correct section; see `docs/baseline-audit.md` for the full note.
- Identified every capability that needs its own OpenSpec change proposal
  (Phase 1–6) and stubbed those directories with one-paragraph scope
  statements, ready for individual approval.
- No behavior, schema, dependency, or API change shipped in this phase.

## Key findings (see `docs/baseline-audit.md` for full evidence)

- Two confirmed, concrete security gaps: (1) `session_store.ensure()` has
  no ownership check, letting a guessable session id pull in another
  user's live conversation context (not a data leak — final SQL is still
  re-authorized against the requester's own scope); (2) SQL regenerated by
  the repair loop (`execute_with_repair`, `pipeline.py:2606-2667`) is
  **never re-passed through `auth.authorize()`**, which is called exactly
  once, upstream, against the pre-repair SQL.
- The SELECT-only Postgres role (proposal 11.1 layer b) is provisioned in
  SQL (`deploy/sql/01_create_megh_app_role.sql`) but that script's own
  header states the service "currently connects as `postgres`
  (superuser)" — unverified as live from the repo alone.
- Postgres row-level security (proposal 11.2's claimed second layer) does
  not exist anywhere — zero `CREATE POLICY` matches repo-wide.
- Five of fifteen pipeline nodes are missing outright: 5.5 (generic
  defaults), 5.8 (schema retrieval as specified — a different RAG system
  exists for FAQ docs, not table/column retrieval), 5.9 (join discovery —
  a well-built curated FK YAML exists per scheme but only its deny-list
  field is read at runtime), 5.13 (result findings), 5.14 (chart
  generator).
- LangGraph, SQLGlot, NetworkX, pandas, Vega/Altair, ClickHouse, and
  Langfuse are confirmed absent from `requirements.txt`/`requirements.lock`
  — none of the proposal's orchestration/validation/observability stack is
  present; production deployment is systemd+nginx on two VMs, not
  Kubernetes.

## Explicitly Out of Scope (this phase and all following phases)

- Legacy Excel ingestion, backfills, quarantine tables, or any ingestion
  CLI (Grant Thornton Section 6 in full). The live database is the only
  data source. Not audited in this phase.
- Rebuilding the application, frontend, or database from scratch.
- Any change to production scheme tables, credentials, or `.env` values.
  `.env` itself was not read during this audit (only `.env.example` and
  SQL/doc files, to avoid handling live credentials).
- Adopting LangGraph, or any other orchestration dependency, as a
  foregone conclusion — Phase 2 records that decision explicitly in its
  own `design.md`, informed by this audit, not before.

## Impact

- No affected capabilities (audit-only). This proposal has no
  `specs/<capability>/spec.md` delta.
- Deliverables: `docs/baseline-audit.md` (full classification tables and
  evidence), plus six stub directories under `openspec/changes/` (Phase
  1–6) each with a one-paragraph scope statement, ready for individual
  approval.

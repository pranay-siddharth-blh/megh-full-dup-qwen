## Purpose

Ensures every SQL statement actually executed against the operational
database — including one regenerated by the automatic repair loop — has
been authorized against the requesting user's role and scope, and that
repair cannot be used as an unauthorized scope-widening path.

## ADDED Requirements

### Requirement: Repaired SQL is re-authorized before execution
The system SHALL re-run authorization, using the requesting user's scope,
in-scope schemes, and resolved entities, against any SQL statement that is
regenerated after an initial statement fails validation or execution,
before that regenerated statement is executed.

#### Scenario: Repair produces a query touching a different scope
- **WHEN** the SQL repair path regenerates a query after a validation
  failure, and the regenerated query differs in tables, columns,
  granularity, or geographic scope from the originally authorized query
- **THEN** the system SHALL evaluate authorization again for the
  regenerated query, and SHALL deny execution and return a denial
  response if that authorization check fails, rather than executing the
  regenerated query

#### Scenario: Repair produces a query within the original authorized scope
- **WHEN** the regenerated query passes the same authorization checks that
  would apply to the original query
- **THEN** the system SHALL proceed to execute it as normal

### Requirement: Repair attempts are capped
The system SHALL limit automatic SQL regeneration for a single user query
to one repair attempt following the initial generation.

#### Scenario: Repeated validation or execution failure
- **WHEN** the initial query and one subsequently repaired query both fail
  validation or execution
- **THEN** the system SHALL stop attempting further repairs and SHALL
  surface an error or fallback response rather than regenerating the
  query again
